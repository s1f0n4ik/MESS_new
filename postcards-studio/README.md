# Postcards Studio

Отдельный веб-сервис для удалённого редактирования четырёх документов инсталляции.

Пошаговая инструкция для ввода текста: [MEDIATOR_GUIDE.md](MEDIATOR_GUIDE.md).

## Что уже входит

- аккаунты медиаторов и роли `editor` / `publisher` / `admin`;
- общий проект с четырьмя документами и 28 страницами в каждом;
- текст, изображения и маски поверх канонического PDF-шаблона;
- одновременное редактирование одного документа несколькими медиаторами без перезаписи чужого текста;
- список присутствующих, автоматическое сохранение, локальный офлайн-буфер и разреженная история контрольных версий;
- экспорт текущего документа в PDF на локальный компьютер;
- явная публикация: сервер собирает четыре PDF и единый `manifest.json`;
- неизменяемые релизы с SHA-256;
- Sync Agent, который безопасно скачивает последний релиз на NAS или админ-ПК;
- работа выставки на последнем загруженном релизе при отсутствии интернета.

PDF является результатом публикации. Источник — структурированный документ, поэтому его можно совместно изменять и повторно собирать без Illustrator.

## Локальный запуск

1. Скопировать `.env.example` в `.env` и сменить пароли и токены.
2. Убедиться, что `STUDIO_TEMPLATE_PDF` указывает на шаблон из 28 страниц.
3. Backend:

   ```powershell
   cd backend
   py -3.12 -m venv .venv
   .\.venv\Scripts\python -m pip install -r requirements.txt
   .\.venv\Scripts\python -m uvicorn app.main:app --reload --port 8081
   ```

4. Frontend:

   ```powershell
   cd frontend
   npm install
   npm run dev
   ```

5. Сервер совместной работы (Node.js 22+):

   ```powershell
   cd collaboration
   npm install
   npm start
   ```

Vite проксирует API на `http://127.0.0.1:8081`, а `/collaboration` — на `ws://127.0.0.1:1234`.

## Docker / VPS

```powershell
Copy-Item .env.example .env
docker compose up --build -d
```

Снаружи должен быть доступен только HTTPS-порт reverse proxy. PostgreSQL не публикуется наружу.
Контейнер `collaboration` хранит бинарное состояние Yjs в отдельном томе; этот том необходимо включить в резервное копирование вместе с PostgreSQL и `studio-data`.

## Production-деплой

GitHub Actions запускается при каждом push в ветку `production`:

1. выполняет тесты API и сервиса совместного редактирования;
2. собирает production-версию интерфейса;
3. только после успешных проверок загружает релиз на сервер;
4. собирает Docker-образы, переключает приложение на новый релиз и проверяет `/api/health`;
5. при неуспешной проверке автоматически возвращает предыдущий релиз.

В GitHub Environment `production` должен находиться секрет `DEPLOY_SSH_KEY`. Файл `.env`, PDF-шаблон и Docker volumes хранятся на сервере отдельно от релизов и при деплое не заменяются.

## Рабочий процесс

1. Администратор создаёт аккаунты медиаторов и отдельно назначает тех, кто может публиковать.
2. Медиаторы открывают один из четырёх документов и вводят текст в готовые поля. Все подключённые к нему участники видны справа вверху; текст синхронизируется сразу. Перемещение объектов, оформление и общий шаблон меняет только администратор в режиме «Настроить макет».
3. При кратком обрыве сети работа остаётся в браузере и отправляется после восстановления соединения.
4. Рабочее состояние сохраняется после каждого изменения, но история получает не более одной автоматической контрольной версии за 15 минут. Публикация и экспорт создают контрольную версию явно.
5. Кнопка «Опубликовать» создаёт неизменяемый комплект из четырёх PDF. Только этот комплект получает Sync Agent и выставочное приложение.

Если в production заданы параметры `STUDIO_YANDEX_DISK_*`, публикация сначала
доставляет комплект напрямую с VPS через официальный REST API Яндекс Диска.
Каждый релиз
попадает в собственную неизменяемую папку, а `current.json` загружается последним.
Контейнер `yandex.disk` на NAS затем синхронизирует эту папку без внешнего доступа
к NAS и без VPN. Для VPS используется отдельный OAuth-токен только с правами
чтения и записи Диска; основной пароль аккаунта в конфигурацию не помещается.

Пользователь с ролью `publisher` или `admin` может переименовать документ
кнопкой с карандашом справа от названия. Новое имя сразу становится общим для
всех участников и используется в имени PDF при локальном скачивании.

## Редактируемый макет и импорт изображений

- «Новый редактируемый макет» создаёт 28 белых страниц с двумя карточками на каждой: фиксированный слот изображения, редактируемая подпись и редактируемое поле основного текста.
- Подпись и основной текст используют настройки шаблона. Браузер загружает шрифты с сервера, чтобы предпросмотр и экспорт использовали одинаковые файлы и межстрочный интервал. Настройки шрифта доступны только администратору.
- Границы штатных полей атрибуции и основного текста автоматически следуют за линиями и контурами. При вставке, наборе, удалении, изменении размера шрифта и границах полей текст автоматически перераспределяется между полем под сканом и продолжением той же стороны открытки на следующем листе. Отдельная кнопка не нужна. Левая и правая колонки независимы. При переполнении обоих полей сверху появляется предупреждение; весь текст сохраняется. Расчёт использует актуальную геометрию редактора, не дожидаясь отложенной записи на сервер.
- По умолчанию атрибуции и основной текст используют Times New Roman с размером 15,3 и базовым интервалом 1,2. У основного текста межстрочный шаг немного подстраивается под целое число строк в фиксированной высоте поля: это убирает остаточный зазор снизу заполненного блока, не перемещая линии и не меняя размер шрифта. Основной текст выровнен по ширине, атрибуция — справа. Приблизительно 4200 знаков относятся к двум полям одной стороны открытки; точная вместимость зависит от длины слов, абзацев и пустых строк. Размер (включая десятые доли) и выравнивание может изменить администратор: «Настроить макет» → выбрать текст → «Размер» / «Выравнивание» → «Сохранить общий шаблон».
- Нижние и боковые штриховые границы сохраняют положение шаблона независимо от объёма текста — и в редакторе, и в PDF. Набор, удаление и автоматический перенос текста не перемещают линии.
- Для готового структурированного макета редактор открывает поля без загрузки исходного PDF и PDF-worker. PDF-фон загружается только для старых документов без собственного фона страниц.
- «Импорт таблицы Word» читает последнюю таблицу файла DOCX, идёт по ней слева направо и сверху вниз, пропускает пустые повторяющиеся заполнители и автоматически размещает изображения по слотам. Изображения вписываются с сохранением пропорций и центрируются.
- Только `admin` может сохранить вёрстку, сканы и атрибуции кнопкой «Сохранить общий шаблон»: они применяются ко всем четырём документам, а основные тексты сохраняются отдельно. Пустой слот скана восстанавливается из заполненного общего материала с тем же кодом скана. Противоречивые подписи из разных документов автоматически не выбираются: администратор сохраняет проверенный вариант из текущего документа.
- Роль `publisher` сохраняет право публикации и переименования документов, но не изменения макета. Сервис совместной работы проверяет каждое обновление медиатора и разрешает только текст существующих полей.

Последовательность сканов соответствует утверждённым разворотам из `SPREAD_SCANS` (`backend/app/editable_template.py` и начальный макет `frontend/src/Editor.jsx`). Администратор может кнопками «↑ Выше» и «↓ Ниже» переставить разворот целиком, а кнопкой «＋ Разворот» добавить новый. Операция выполняется сразу во всех четырёх документах и переносит оба листа блока вместе со сканами, атрибуциями и основным текстом. Перед изменением сервер сохраняет предыдущее состояние; после операции необходимо проверить все четыре документа и только затем публиковать комплект. Медиаторам эти команды недоступны.

Атрибуция и основной текст хранятся в разных полях независимо от видимой линии между ними. В текущем интерфейсе нет отдельной надёжно проверенной команды «скрыть разделительную линию», которая заявлена как штатная пользовательская функция. Универсальные операции с объектами макета не следует считать эквивалентом такой команды без отдельной проверки.

У изображения также нет штатного свойства «контур изображения». Добавление обычной прямоугольной фигуры поверх слота является ручным обходным приёмом, а не встроенной функцией контура. Чёрный заполнитель использует фиксированное отображение внутри слота; отдельная настройка его контура в интерфейсе не предусмотрена и совпадение с образцом не гарантируется.

Импортированная нумерация показывается при выборе изображения. Подписи из ячеек Word сохраняются как служебные метки и не печатаются поверх открыток.

Перед первым production-запуском задайте уникальные `STUDIO_SECRET_KEY`, `STUDIO_ADMIN_PASSWORD`, `STUDIO_SYNC_TOKEN` и `STUDIO_COLLABORATION_SECRET`. После первого входа создайте именные учётные записи; общий пароль между медиаторами использовать не следует.

## Sync Agent

```powershell
py -3.12 sync-agent\agent.py `
  --server https://studio.example.org `
  --token YOUR_SYNC_TOKEN `
  --destination "\\NAS\Postcards\releases" `
  --application http://127.0.0.1:8787 `
  --interval 30
```

Агент скачивает файлы во временный каталог, проверяет размер и SHA-256, устанавливает комплект в локальное приложение и затем атомарно обновляет `current.json`. Никакие SMB-порты NAS в интернет открывать не требуется.

Если на отдельном Windows-ноутбуке уже подключена синхронизируемая папка NAS / Яндекс Диска, контейнер на NAS не требуется. Установите агент как задачу текущего пользователя и укажите отдельную подпапку для релизов:

```powershell
.\install-windows.ps1 `
  -Server 'https://mess-studio.ru' `
  -Token 'значение STUDIO_SYNC_TOKEN' `
  -Destination '\\MESS-NAS\MESS\Yandex.Disk\Выставка Анастасии Чермантеевой\Postcards Studio\Релизы' `
  -Application 'http://127.0.0.1:8787'
```

Токен сохраняется не в аргументах задачи, а в закрытом файле `%LOCALAPPDATA%\PostcardsStudio\sync-token`. Задача запускается при входе пользователя и повторяет синхронизацию каждые 30 секунд. Ноутбук должен быть включён, пользователь должен войти в Windows, а указанный сетевой каталог должен быть доступен этому пользователю.

Для админ-ПК предпочтителен UNC-путь, показанный выше: он не зависит от буквы
подключённого диска. Агент сначала записывает и проверяет релиз в общем архиве
NAS, а затем передаёт этот уже проверенный каталог локальному координатору на
`127.0.0.1:8787`. Координатор атомарно устанавливает четыре PDF в рабочий кеш.

## NAS UGREEN и Яндекс Диск

Правильная схема не требует внешнего туннеля и не передаёт пароль от Яндекса на VPS:

1. `postcards-sync` работает контейнером непосредственно на NAS и по HTTPS забирает только опубликованные релизы с `mess-studio.ru`.
2. Контейнер пишет релизы в отдельную подпапку каталога, который уже смонтирован в `yandex.disk` как `/root/Yandex.Disk`.
3. Существующий `yandex.disk` синхронизирует эту подпапку с облаком. Каждый релиз хранится в каталоге с датой и номером, а `current.json` указывает на актуальный комплект.

Перед запуском в UGREEN Docker откройте настройки существующего контейнера `yandex.disk` и найдите host path для `/root/Yandex.Disk`. Создайте внутри него каталог `Postcards-Studio` и укажите полный путь в `NAS_POSTCARDS_PATH`.

```bash
cd sync-agent
cp nas.env.example nas.env
# заполнить POSTCARDS_SYNC_TOKEN и NAS_POSTCARDS_PATH
docker compose --env-file nas.env -f docker-compose.nas.yml up -d --build
docker compose --env-file nas.env -f docker-compose.nas.yml logs -f
```

Не добавляйте `nas.env` в Git и не помещайте пароль Яндекса в конфигурацию Postcards Studio. Авторизационные данные Яндекса остаются только в конфигурационном томе уже установленного контейнера `yandex.disk`.
# Отдельные версии документа 4 во время медиаций

В десктопе версии 2.0.4 на четвёртом круге кнопка «Изменить» открывает встроенный редактор Studio. Для открытия и обмена нужен интернет. Сотрудник создаёт отдельную медиацию из редактируемого исходника установленного PDF4. Если старый релиз не содержит исходника и его нельзя восстановить из истории, редактор предлагает опубликовать новый комплект и синхронизировать приложение.

Каждая медиация — отдельный документ с собственным гостевым логином и паролем. Гости могут изменять только основной текст своей версии; сканы, атрибуции и геометрия защищены и на сервере. Пароль показывается один раз при создании. Сайт сохраняет правки автоматически. «Сохранить на NAS» создаёт версионный архив `Медиации/<projectId>/r<revision>/`: редактируемый JSON, PDF и manifest с контрольными суммами. При переполнении исходник сохраняется полностью, а PDF не выдаётся как корректный. Архив передаётся существующей доставкой Яндекс Диска либо обновлённым sync-agent; выставочный `current.json` не заменяется.

Администратор открывает медиацию на сайте и нажимает «Перенести в общий документ 4». Тексты переносятся через совместный редактор с сохранением истории. После проверки администратор отдельно публикует обычный комплект четырёх PDF. Редактирование гостями само по себе ничего не публикует.

Координатор десктопа запоминает выбранную медиацию для текущего запуска сценария в `data/mediation-selections.json`, без паролей. Адрес Studio задаёт `POSTCARDS_STUDIO_URL` (по умолчанию `https://mess-studio.ru`). Обновите приложение и сервер-координатор; для NAS с прямым sync-agent обновите также `sync-agent/agent.py`. При доставке через Яндекс Диск обновление NAS-агента не требуется.
